# Hardened blob reads re-validate the commit on every call

`readCommittedBlob` calls `assertSourceCommit` on every invocation, which
spends three Git processes re-validating the same commit before the two that
actually read the blob.

Measured on this vault at `e70d4ac4`: **48.8 ms per call**. At 2,453 payloads
that is **~96 s to build** and **~99 s to verify**, and `pnpm
artifact:check-determinism` pays it twice.

The per-call self-validation is deliberate — it is what lets any caller trust
a single read without holding a validated handle, and PR #8's
integrity/provenance split leaned on that property. So this is not a defect to
patch in passing.

Two candidate fixes, both security-shaped API decisions that deserve their own
scoped PR:

1. **Hoist the validation.** `buildPrivateArtifact` and
`verifyPrivateArtifact` validate the commit once and read blobs through an
internal path that skips it. Cheapest, but it splits `readCommittedBlob` into
a checked and an unchecked variant, and the unchecked one is exactly the thing
a future caller reaches for by accident.
2. **A batch API taking an already-validated handle.** `assertSourceCommit`
returns an opaque token that a `readCommittedBlobs` accepts, so the type
system carries the proof that validation happened. More code, no unchecked
path to misuse.

PR #10's pipeline sidesteps this for *selection* only, with a pipeline-local
batch reader — legitimate there because selection is not a trust boundary and
every selected path is re-read through the hardened path afterward. Build and
verify have no such escape.

No action needed unless the build time becomes intolerable; the measurement is
recorded here so the decision starts with evidence.

# P2: terminal readability — real newlines and the command-output cap

Both items are output readability, and both sit on top of the terminal-control
escaping that `src/app-server/terminal.ts` exists to provide. Neither is a
correctness or safety defect, and neither blocked a run across the fifteen

## 1. Newlines render as a literal `\x0A`

`TERMINAL_CONTROL_PATTERN` in `src/app-server/terminal.ts:1` is
`/[\p{Cc}\p{Cf}\p{Zl}\p{Zp}]/u`, which matches `\n` alongside every other C0
control, so `escapeTerminalPart` turns it into `\x0A`. Every multi-line answer
arrives as one unbroken run per chunk.

**Exempting `\n` from that pattern is the wrong fix** and would reopen the
spoofing surface the escaping exists to close: `\r`, CSI, OSC, and the bidi
overrides all still have to reach the terminal visibly escaped, and a bare
`\n` passed through beside them lets a crafted message paint lines that look
like the harness's own output.

The fix is structural instead: split the value on `\n` before escaping, and
emit each resulting segment as its own rendered line, each still bounded by
`boundedTerminalText` and still carrying its ordinal tag. Every other control
character keeps its current escape.

Acceptance:

- A message containing `\n` renders across several lines and no line contains
  the two characters `\x0A`.
- A message containing `\r`, `\x1b[31m`, an OSC 8 hyperlink, and `U+202E`
  still renders each of them escaped and visible.
- The per-line byte bound holds on every emitted segment.
- The existing prefix-reprint property still holds: no rendered line for an
  item id is a strict prefix of a later line for the same id.

## 2. `Command output:` is truncated at the ordinary rendered-value cap

`src/app-server/renderer.ts:150` renders command output through `bounded(...)`
at `MAX_RENDERED_VALUE = 512`.

This is a **different cap from the message path**. `#7` removed
`MAX_TEXT_LENGTH` and gave completed messages the chunked
`MAX_RETAINED_TEXT_BYTES` path at `renderer.ts:20`; command output was not
part
of that change and still takes the 512-byte single-line bound. Re-patching the
message path does not touch this.

Whether command output should get the same chunked treatment, a larger
dedicated cap, or stay bounded on purpose is the open question — the reducer
bounds what it retains as well, so raising the renderer alone would not
necessarily surface more.

Acceptance, once the policy is chosen:

- The chosen bound is named in one place and the renderer reads it from there.
- A command whose output exceeds the bound renders with the truncation marker
  rather than silently short output.

`mergeReceiptOcrPages` accepts four kinds of non-overlap as a proven seam,

## The defects

### 1. A single identical row proves a seam

Buying two of one item prints the identical row twice. A page ending with that
row and the next page beginning with it match exactly **without overlapping at
all**.

`leftCount = 1`, `rightCount = 1` → 25 normalized characters clears

`_minimumSingleLineSimilarity` (0.92) → accepted. One real purchase is
deleted.

### 2. Single-line approximate match deletes a repeat purchase

```
서울우유 1L 흰우유 990ml    1     2,000
서울우유 1L 흰우유 990ml    2     4,000
```

25 normalized characters, similarity **0.9200** — exactly at
`_minimumSingleLineSimilarity`. Accepted; the second purchase is deleted.

### 3. The same mechanism one window wider

Page 0 ends with quantities 1 and 2, page 1 begins with quantities 3 and 4 of
the same product, with no overlap between the captures:

39 normalized characters, length ratio 0, similarity **0.8974** ≥
`_minimumWindowSimilarity` (0.85). Accepted; two real purchases are deleted.

**Tightening the single-line floor does not fix this** — that was tried in the
RN port and this case cleared the multi-line floor by the identical mechanism.
The root cause is that the digits carry all the meaning and almost none of the
edit distance, so no similarity floor separates "the same line, misread" from
"a different purchase" on receipt text.

### 4. A shallow coincidence beats a deeper true overlap

`_maxWindowLines = 8`, so a nine-line overlap is never built as a window. A
receipt repeating a separator and a section header at both ends of the
overlapped region — `[A, B, C, D, E, F, G, A, B]` — matches at two lines with
`similarity = 1.0`.

Result: two lines dropped, seven left duplicated, seam reported proven.
Measured in the RN port as 18 output lines where 11 were correct.

This one is **not** fixed by requiring exact equality — both the shallow and
the deep match are exact.

## What the RN port did

- Removed approximate matching entirely. Seam matching requires normalized
equality; the Levenshtein pass, the 512-character cost guard, the length-ratio
prefilter and both similarity floors are gone. Closes 2 and 3.
- Removed the window cap and scan suffix/prefix depths **deepest-first**,
returning the first depth that matches. Closes 4, and overlaps of any depth
now merge.
- Require the matched region to hold **two distinct lines**. Closes 1, and
also the variant where four identical rows split 2/2 across the boundary match
at depth 2.

ms to 3 ms — comparing pre-normalized line arrays with an early exit is
cheaper than building joined windows and running an edit distance, even though
the deepest-first scan is O(n²) worst case.

seam is visible in `unmatchedBoundaryIndexes` with the text intact, while a
deleted row is invisible. If device data later shows too many unproven seams,
the upgrade path is a digit-aware comparison (equal digit runs, fuzz
elsewhere), never a looser floor.

precedent 조회는 에이전트 저장소의 디스크 공간 부족으로 시작 자체가 실패했습니다(`[TOOL_FAILED]`). 이 결정에는 현재
저장소의 명시적 계약과 구현·테스트가 충분한 1차 근거이므로, 외부 precedent를 추정하지 않고 그 근거만으로 방향을
마무리하겠습니다.## 결정

병합은 **정규화된 동일 줄 배열의 정확한 일치만** seam으로 인정해야 합니다.

인접 페이지마다 공통 가능한 깊이 전체를 가장 깊은 쪽부터 검사합니다. 동일한 깊이의 suffix/prefix가 정확히 같고, 그 구간에
**서로 다른 정규화 줄이 최소 두 개** 있을 때만 다음 페이지의 해당 prefix를 제거합니다. 첫 일치가 곧 선택 결과이며,
상한·점수·tie-break는 없습니다.

일치하지 않으면 현재 계약대로 다음 페이지 텍스트를 전부 보존하고 `unmatchedBoundaryIndexes`에 경계를 기록해
`isComplete: false`를 반환합니다. 공개 모델이나 네이티브/Pigeon 경계는 바꾸지 않습니다.

## 거절하는 선택

- Levenshtein 유사도, 문자 수·길이 비율·512자 비용 제한, 단일/다중 줄 similarity floor: 숫자만 다른 실제
구매 행을 seam으로 오인하므로 제거합니다.
- 정확 일치만 남기되 8줄 상한 또는 최고 점수 선택을 유지하는 안: 9줄 이상의 진짜 overlap보다 얕은 반복
header/separator를 선택할 수 있으므로 거절합니다.
- 단일 줄 exact match, 또는 같은 줄만 반복된 2줄 match: 반복 구매와 `A/A`류 경계를 증명할 수 없으므로 거절합니다.
- “exact 실패 시 fuzzy fallback”: 현재 결함을 다른 경로로 되살립니다. 장치 데이터에서 미증명 seam이 과도하다고
확인되기 전까지 넣지 않으며, 후속 개선은 digit run을 동일하게 요구하는 별도 digit-aware 비교여야 합니다.

## 저장소 근거와 제약

현재 [병합기](/Volumes/dongminyu/Development/01_personal/flutter_receipt_scanner/fl

실패 경로를 제공하므로, 더 관대한 추론을 추가할 이유가 없습니다.

[명세의 OCR Merge 절](/Volumes/dongminyu/Development/01_personal/flutter_receipt_s

설명해야 합니다: 인접 경계, line-level normalization, 깊이 제한 없는 deepest-first exact
equality, 두 distinct line 최소 조건, 미증명 시 보존·진단. 따라서 기존 tie-break와 비용 guard는
명세에서도 삭제합니다.
