# Note: the v0.2 Oracle acceptance measurement

Date: 2026-08-26

Runs the measurement specified in
`docs/specs/2026-08-25-v0.2-oracle-acceptance.md`. That document's criteria
were fixed before the first run and are not restated or revised here.

**Outcome: the measurement does not pass, and the reason is one mechanism
rather than five task outcomes.** In four of five treatment runs the Oracle
retrieved precedent that bears on the task's fork, with citations that resolve
to what they claim. None of it reached the written direction. No direction in
any of the ten runs contains a single `wiki/<path>.md:<line>` citation, so the
retrieval criterion fails on every task, and every task is a null result on the
direction criterion.

## What was run

Ten runs, control first in each pair, stdin from `/dev/null`. The target's
`HEAD` was read before and after every arm and never moved.

| Task | Target                      | Revision   | Oracle | Cites wiki |
| ---- | --------------------------- | ---------- | ------ | ---------- |
| 1    | `bubble_shooter#43`         | `7d9dd4f`  | yes    | no         |
| 2    | `llm-wiki-dongminyu#9`      | `77d4bebc` | yes    | no         |
| 3    | `bubble_shooter#38`         | `7d9dd4f`  | yes    | no         |
| 4    | `andrew-code-agent#10`      | `d491d92`  | yes    | no         |
| 5    | `flutter_receipt_scanner#3` | `558bffa`  | no     | no         |

Every run ended `Terminal status: completed`, and no target repository was
modified by any run.

## Deviations from the plan, recorded rather than smoothed over

- **Task 2 ran against a clean local clone** of the wiki at `77d4bebc`. The
  working copy carried 55 uncommitted files belonging to the operator, and the
  product requires a clean target worktree. The Oracle root stayed the real
  wiki, whose freshness labels are derived from its history.
- **The prompt carries a wrapper that is mine.** Each prompt is the issue title
  and body verbatim between two markers, followed by a fixed instruction block,
  identical on both arms of every task:

  ```plaintext
  An issue is open in the repository you are working in. Its full text follows.

  --- issue ---
  <issue title and body, verbatim>
  --- end of issue ---

  Write a design direction for this issue and reply with it in your message.

  Say which decision you would take, what you reject and why, and which
  constraints bear on the choice. Ground it in the repository as it stands and
  read whatever you need to.

  Do not modify any file, do not commit, and do not open a pull request. The
  written direction is the whole deliverable.
  ```

  Carrying the issue text is forced, not chosen for convenience: a managed run
  has no network and declines the escalation it raises about it, so the agent
  cannot fetch an issue. `docs/notes/2026-08-26-managed-run-network-boundary.md`
  owns that measurement. The wrapper names no wiki, page, or prior decision.

- **Task 4's treatment ran twice.** The first attempt was killed at a
  ten-minute tool timeout, which left a `run.lock` whose owner process was
  gone. The product refuses a stale lock rather than recovering it, which is
  the documented choice, so the lock was removed by hand after confirming the
  owner pid was dead, and the run was re-issued in the background. Only the
  completed run is reported.

## The leak scan

Built from the wiki's `sensitive: true` files, and **made to fail before its
pass was trusted**: a marker planted in a synthetic log was reported as a hit,
and a clean log passed.

- 22 files carry the marker. 19 of them yield distinctive shingles, 760 in
  total, where distinctive means the shingle appears in no other file in the
  wiki.
- Three yield none, because their text also exists in a file that is not marked
  sensitive. A hit on those could not be attributed to the sensitive copy, so
  the scan covers 19 of 22 files and this note says so rather than reporting
  coverage it does not have.
- Every run log was scanned the moment its run exited, not batched at the end,
  because a hit stops the measurement and a batched scan would have put the
  remaining runs on the terminal first.
- **All ten logs are clean.**

## The stale claim, re-derived at measurement time

The specification requires re-deriving one rather than naming one in advance.

- Claim: `wiki/concepts/home-git-root-hazard.md:30` and `wiki/overview.md:124`
  both state that `/Volumes/dongminyu/Development/01_personal` is itself a Git
  root, the first citing a 2026-07-25 verification.
- Check, 2026-08-26: `git -C /Volumes/dongminyu/Development/01_personal
rev-parse --show-toplevel` fails with `not a git repository ... Stopping at
filesystem boundary`. The claim is stale.
- No run stated it, and no run had reason to: none of the five forks touches
  repository nesting. The criterion is therefore **untested**, which is the
  outcome the specification prescribes over a pass that could not fail.

## Per task

### Task 1 — `bubble_shooter#43`, the abandoned run's high score

Both arms decide the same thing at the named fork: `abandonRun()` must not
finalize the run, the high score must persist separately from `run_end` and the
interstitial cadence, and the stored value is the truth the displayed Best has
to match. They differ only in where the score is captured — the control adds a
score provider at `attach()`, the treatment passes it at `detach()` and awaits
the write.

The Oracle returned three citations. All three were opened and all three say
what it claimed:

- `wiki/sources/…bubble-shooter--memory--meta-ui-open-decisions.md:33` records
  this exact defect, the losing sequence, and the fix shape: pass the score
  `dispose()` already holds into `abandonRun` and check-and-save before the
  phase guard. Bears on the fork.
- `wiki/sources/…bubble-shooter--memory--shared-prefs-reload-is-vacuous.md:30`
  is the memoised-singleton ruling: a second `load()` re-reads the cache it just
  wrote. Bears on the fork's verification.
- `wiki/concepts/evidence-basis-discipline.md:46` is the general
  make-it-fail-first principle. Adjacent, and the Oracle labelled it as general
  rather than resting on it.

The treatment's capture site is the one the precedent proposes and the control's
is not. That is not the named fork, so it is recorded as an observation and not
counted.

**Retrieval: fails. Direction: null.**

### Task 2 — `llm-wiki-dongminyu#9`, hardened blob reads

Both arms choose the opaque validated-handle batch API, keep per-call
validation on the single read, and reject the unchecked reader. Both
independently require a runtime identity registry rather than a type-level
brand, so that a cast or deserialized object is refused, which contradicts
the issue body's own claim that the type system carries the proof. The treatment
adds a re-derived path count against the issue's older figure.

The treatment states in its own words that the Oracle found no direct precedent
for this choice, only an adjacent principle.

**Retrieval: fails. Direction: null.**

### Task 3 — `bubble_shooter#38`, UMP and ATT ordering

Both arms make the AdMob UMP IDFA message the sole owner of ATT and reject a
separate `ATTrackingManager` call.

The Oracle's own record for this task holds 51 distinct `wiki/<path>.md:<line>`
matches, which is what it read and composed; it returned three, two of which are
squarely on the fork. Both were opened and both hold:
`…ump-form-futures-await-dismissal.md:32` and `:40` establish that the consent
form's future completes on dismissal and that `canRequestAds()` is the
authority; `…att-not-implemented.md:37` records that ATT was left out of
PR #19 deliberately and is requested conditionally through the UMP flow.

So precedent existed, bore on the fork, and the control reached the same place
without it. Agreement alone is a null result and is recorded as one.

**Retrieval: fails. Direction: null.**

### Task 4 — `andrew-code-agent#10`, newlines and the output cap

Both arms split structurally on `\n` while leaving the escape pattern intact,
and both keep command output bounded rather than giving it the message path's
chunking. The treatment's supporting argument, that the reducer already
bounds what it retains so raising the renderer alone surfaces nothing, is
stated in
the issue body, which the specification explicitly refuses to count.

**Retrieval: fails. Direction: null.**

### Task 5 — `flutter_receipt_scanner#3`, what counts as a proven seam

The treatment run **never consulted the Oracle**. Its own message reports the
subagent failing to start for lack of disk space, and the session record
confirms it: `No space left on device`, with 5.7 GiB free on the root volume at
the time. The run then said so and finished on repository evidence alone rather
than inventing precedent, which is the correct behaviour, but it means this task
has no treatment arm in the sense the measurement needs.

**Retrieval: fails, for a different reason than the other four. Direction:
null.**

Task 5 contributes a failure to the first row that was never measured: its

The irrelevance criterion is recorded as untested rather than passed. It fails
when a page that does not bear on the fork is used as grounds, and no direction
rested on any wiki page at all, so nothing could have failed it. Task 2 comes
closest to a pass on its own terms, because its direction marks the Oracle's
return as not directly applicable and says why, which is one of the stated pass
conditions; one task doing that does not make the criterion testable across the
five. The
specification's own posture is that a criterion which cannot fail is not
evidence.

## What the measurement found instead

The Oracle works. It scopes to the project and account, labels freshness,
returns citations in the required `wiki/<path>.md:<line>` form, and the
citations resolve — every one opened here said what it claimed, across two
tasks and six citations. In task 1 and task 3 it returned the precedent the
specification anticipated.

What does not happen is propagation, and it fails at the last step rather than
at the subagent boundary. Counting distinct `wiki/<path>.md:<line>` matches in
each run's own session record, the Oracle's answer reached the **parent's**
context carrying 3, 4, 8 and 4 citations for tasks 1 to 4. The parent's written
direction then carried none of them, citing repository files instead. The
capability's instruction section tells the agent to consult the Oracle and to
weigh what it returns; it does not ask the agent to carry the grounds into its
answer, and the agent does not.

**Which reading of the retrieval criterion this uses.** The criterion says the
treatment run cites at least one wiki page. This note reads that as the written
direction citing one, because the direction is the deliverable and the
specification's recording section asks for the citations that were opened and
checked, which presupposes citations in what was delivered. Under the other
available reading, where the subagent's answer counts as part of the run,
retrieval would be 4 of 5, and the evidence above supports that reading on the
facts. The verdict does not move either way: three of five must also count on
the direction criterion, and that one is 0 of 5 on its own. The distinction
matters for what to fix, not for the outcome, and it points at propagation
rather than at retrieval.

That is a finding about the product, not about precedent, and it is the reason
this measurement returns zeroes. It cannot be fixed by rewording the prompt:
the specification forbids a prompt that names the wiki, and two earlier prompt
revisions already moved what was being measured.

## Residual friction

- A run killed mid-flight leaves a stale `run.lock` that the next run refuses.
  That refusal is deliberate, but there is no `--force` or `doctor --repair`
  path, so recovery is a manual file deletion.
- The root volume ran out of space during the tenth run and took the Oracle
  subagent down with it. Nothing in the product reports this as a blocker;
  it surfaced only as the agent's own `[TOOL_FAILED]` line and, underneath it,
  a `No space left on device` in the session record.
- A design-direction run against this repository exceeded ten minutes, which is
  worth knowing before scheduling a batch of them.
