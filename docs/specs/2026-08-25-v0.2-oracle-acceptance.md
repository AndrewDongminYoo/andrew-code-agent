# Specification: v0.2 Oracle acceptance measurement

Date: 2026-08-25
Measures: the last three lines of the Definition of Done in
`docs/plans/2026-08-25-v0.2-oracle-capability.md`, which are measured by running
the agent rather than by a test.

**Every criterion below is fixed before the first run.** Deciding afterwards
what counts as help is how a measurement returns whatever it was set up to
return, and the first three code steps of this milestone each shipped a check
that could not fail until a revert pass exposed it.

## What is being measured

- Across five real tasks where past decisions matter, relevant precedent is
  retrieved.
- In at least three of those five, the retrieval demonstrably changed a design
  decision or an implementation direction.
- Irrelevant or stale retrieval is not treated as authoritative fact.

## Why each task runs twice

A single Oracle-enabled run cannot distinguish precedent that changed the
outcome from a model that would have reached the same place unaided. Each task
therefore runs twice against the same target revision:

- **Control** — no flag. Also confirms in real use what the digest comparison
  asserts structurally: a run without the capability behaves as v0.1 does.
- **Treatment** — `--capability oracle` with `ANDREW_AGENT_ORACLE_ROOT` set.

Run the control first. Reading the treatment first makes the control look like
a lesser version of it.

Both runs get the same prompt, and the prompt never names the wiki, a page, or a
prior decision. A prompt that points at the answer measures nothing.

## The tasks

Ordered deliberately. `flutter_receipt_scanner` is the only public repository
among them and is last, so it is attempted only after the leak scan below has
come up clean on four private ones.

1. **`bubble_shooter#43`** — the fork is whether `abandonRun()` persists, and
   whether the displayed Best or the stored one is the truth. The precedent
   that should bear on it: a 2026-08-15 incident that destroyed real scores and
   streaks, and the ruling that a reload through a memoised singleton is a
   vacuous test.
2. **`llm-wiki-dongminyu#9`** — safety against cost. Per-call commit
   re-validation is deliberate and the issue says so. Precedent: that
   repository's own artifact-kernel decisions.
3. **`bubble_shooter#38`** — the ordering of UMP, ATT, and ad initialisation.
   Precedent: prior store-policy work on other apps.
4. **`andrew-code-agent#10`** — structural newline splitting against exempting
   `\n` from the escape set. Precedent: terminal-control spoofing decisions.
5. **`flutter_receipt_scanner#3`** — what counts as a proven seam. Precedent:
   six review rounds on the sibling port's PR #19.

Each task's deliverable is a **written design direction**, not a merged change.
Nothing from these runs is committed to a target repository as part of the
measurement.

## Criterion for "relevant precedent was retrieved"

Counts only when **all** hold:

1. The treatment run cites at least one wiki page by `wiki/<path>.md:<line>`.
2. The cited page bears on the fork named in the table, not merely on the
   repository or the language.
3. The citation is checked by opening the page. A citation that does not
   resolve, or resolves to a page that does not say what the run claims, counts
   as a failure of this criterion rather than as a retrieval.

## Criterion for "demonstrably changed the direction"

Counts only when the control and the treatment **differ**, and the difference
is one of:

- The treatment reaches a different decision at the named fork.
- The treatment reaches the same decision but rejects an alternative the
  control left open, citing the reason.
- The treatment names a constraint the control missed, and that constraint is
  in the cited page.

Explicitly does **not** count:

- The treatment being longer, better organised, or more confident.
- The treatment restating a constraint already written in the issue body. Three
  of these five issues state their own trap; repeating it is not retrieval.
- Agreement alone. Both runs reaching the same place is a null result, and a
  null result is recorded as one.

Three of five must count. Fewer is a real outcome and is recorded as such.

## Criterion for "stale retrieval is not treated as authoritative"

The adapter already labels each item `CURRENT | STALE | UNVERIFIED` and dates it
from Git history, so this criterion tests whether the caller honours the label.

Two entries are known to be stale as of 2026-08-25, both measured today:

- The claim that `/Volumes/dongminyu/Development/01_personal` is itself a Git
  root. It is not; `rev-parse --show-toplevel` fails there.
- The claim that `main` on `andrew-code-agent` has no branch protection. It is
  protected by a repository ruleset; the legacy endpoint's 404 is what
  ruleset-based protection returns.

At least one task must be chosen or extended so one of these is in scope.
The criterion **fails** if a run states the stale claim as current fact, and
**passes** if the run either omits it, marks it stale, or re-derives it.

This is the one criterion that can fail without any task failing, which is why
it is stated separately rather than folded into the count above.

## Leak scan

The Oracle root is the whole wiki, on purpose. A filtered copy was considered
and rejected: a fresh `git init` flattens the history the freshness labels are
derived from, which would disable the criterion above before it ran; and
deleting the files from a clone leaves them reachable through `git show`.

The gate therefore sits at recording rather than at reading. Before any run's
output is written into a note:

1. Scan the run log and the written direction for distinctive strings from the
   wiki files marked `sensitive: true`.
2. **Make the scan fail first.** Plant one such string in the text, confirm the
   scan reports it, remove it, then scan clean. A scan that has not been seen
   to fail is not evidence.
3. A hit stops the measurement rather than being edited out, because a hit
   means the boundary is in the wrong place, not that one sentence was unlucky.

The paths are enumerated by `grep -rl 'sensitive: true'` against the wiki root
at the moment of the scan, and the count is deliberately not written down. It
moved from sixteen to twenty-two within hours of this document being written,
because the vault is a live repository that other sessions write to. A number
copied here would have been wrong before the first run.

## Recording

One note in `docs/notes/`, in the shape the two v0.1 dogfooding notes use: what
was run, what moved, what did not, and the residual friction. Per task it
records the prompt, both runs' directions, which criteria counted, and the
citations that were opened and checked.

A criterion that was not met is recorded with what happened instead. The
measurement is only worth running if it is allowed to come out badly.
