# Plan: v0.2 Oracle Capability

Date: 2026-08-25
Baseline: `v0.1.0`
Branch: `feat/v0.2-oracle-capability`

v0.1 froze a Codex harness whose personalization is unreachable: the bundle
layer already renders and gates an `oracle` capability, and the CLI asks for
none, so no operator can turn it on.
This plan closes exactly that gap and nothing else.

Each step names the change and the command that decides whether it worked.

## What already exists

The capability machinery is built and tested below the CLI.
Re-derive these from the code rather than from this list if they stop
matching:

- `src/bundle/render.ts` gates files, hooks, and instruction sections on the
  enabled capability set, resolves `oracle` only when an absolute readable
  `llmWikiRoot` is supplied, and asserts that capability's declared
  requirements once it is enabled.
- `src/bundle/artifact.ts` normalizes the requested set, and refuses a
  capability input that was not requested with `UNREQUESTED_CAPABILITY_INPUT`.
- `src/bundle/install.ts` folds `requestedCapabilities` into the digest input,
  so two capability sets are two different bundles.
- `test/integration/live-manifest.test.mjs` is the only caller that requests
  one today.

What is missing sits above and beside that machinery, in two places rather
than one.
`prepareCandidate` in `src/commands/run.ts` passes `requestedCapabilities: []`
and `capabilityInputs: {}` unconditionally, and `src/cli.ts` parses no flag
that could change it — that is the reachability gap.
Separately, the rendered configuration keeps `${LLM_WIKI_ROOT}` as a literal
and no part of the product expands it, while the App Server child is spawned
with two environment variables that do not include it.
Requesting the capability without closing the second gap would produce a run
that validates, installs, and then cannot resolve the wiki; step 3 covers it.

## Scope

In scope: the `oracle` capability, opt-in, default off, on `run` and `resume`.

Out of scope, and each of these stays out for v0.2:
`shared-memory` in any form including reads, any write path back into the
wiki, a GUI, cloud execution, and multi-agent orchestration.
`src/bundle/render.ts` already refuses a manifest declaring anything other
than `oracle`, and that refusal stays.

## 1. Parse the capability flag

Add `--capability <name>` to `run` and `resume` in `src/cli.ts`.
The flag is repeatable, accepts only `oracle` in v0.2, and rejects an unknown
name with the usage exit code rather than ignoring it.
Absent the flag the requested set is empty and the run is byte-identical to
v0.1: the same bundle digest, because the digest input is unchanged.

The Oracle root is not a second flag.
Read it from `ANDREW_AGENT_ORACLE_ROOT`, which joins the four existing runtime
variables and keeps the operator's wiki path off the command line and out of
shell history.
Requesting `oracle` without that variable set fails with a named diagnostic;
it is never silently downgraded to a run without the capability.

- Verify: `node --test test/integration/cli.test.mjs` covers the accepted
  flag, a repeated flag, an unknown name at exit 2, and `oracle` requested
  with the variable unset.
- Verify the default is unchanged: a run with no flag produces the same
  `bundleDigest` as the same source tree produced before this step.

## 2. Thread the set through `prepareCandidate`

Give `prepareCandidate` the requested set and the capability inputs as
parameters instead of the two literals, and have `runCommand` pass what the
CLI parsed.
`resolveRuntimePaths` gains the Oracle root so path canonicalization and the
existing overlap rejection cover it too.

- Verify: `pnpm test:integration` passes with a fake that asserts
  `buildBundle` received the requested set.
- Verify the failure path: request `oracle` against a bundle source whose
  manifest declares no such capability, and confirm the run aborts naming the
  refusal rather than proceeding without it.

## 3. Forward the root to the App Server child

Steps 1 and 2 get the root as far as validation and the bundle, and that is
not far enough to work.
`agent-bundle.toml` rewrites the operator's literal wiki path back into
`${LLM_WIKI_ROOT}/` before the file is bundled, and
`assertDisabledCapabilityTokens` in `src/bundle/render.ts:604` skips the check
for an _enabled_ capability, so the installed `agents/oracle.toml` ships that
token verbatim and nothing in the product expands it.
Meanwhile `startAppServer` spawns Codex with `env: { CODEX_HOME, PATH }` and
nothing else (`src/app-server/client.ts:101`).
Without this step a `--capability oracle` run passes root validation, installs
a config naming a variable, and launches an adapter that cannot resolve it.

Map `ANDREW_AGENT_ORACLE_ROOT` to a child-only `LLM_WIKI_ROOT` in
`appServerInput`, and add it to the spawn environment only when the capability
is enabled.
The environment stays explicitly constructed rather than inherited: the two
existing variables plus this one, never a copy of `process.env`.

- Verify the contract, not just the happy path: `pnpm test:integration` covers
  an Oracle-enabled spawn carrying exactly three variables, and an
  Oracle-disabled spawn carrying exactly the existing two.
- Verify it is not vacuous: assert the enabled case fails when the mapping is
  removed, before trusting that it passes.

## 4. Bind the thread to the capability set and the root it was granted

`ThreadRecord` carries no capability field, so `resume` cannot today tell what
the original run was granted.
Add `requestedCapabilities` to the record at a new schema version, and read a
record written without it as the empty set, in the shape the installer already
uses for its schema 1 records.

**The capability name alone does not hold the boundary.** A thread started
against root A and resumed after `ANDREW_AGENT_ORACLE_ROOT` moved to root B
carries the same `["oracle"]` either way, so a name-only comparison accepts
the resume and rebuilds the adapter against a different data scope.
Record a root identity beside the set and compare that too: the SHA-256 of the
canonical `realpath`, never the path itself, so the record binds the scope
without writing a personal path into the state tree.
A resume whose root hashes differently is refused the way a disagreeing flag
is, and the diagnostic says the root changed without naming either one.

`resume` derives both from the record it read, and refuses a `--capability`
flag that disagrees.
Deriving from the record rather than from the flag or the environment is what
makes the boundary hold: a resumed thread cannot be widened after the fact.

Comparing the rebuilt `bundleDigest` against the recorded one was considered
and rejected: the digest also moves when the bundle source tree changes, so a
mismatch could not distinguish a widened capability from an ordinary bundle
update, and every legitimate resume after a bundle change would break.

- Verify: `node --test test/integration/thread-store.test.mjs` covers the new
  fields, the legacy record read as empty, and a corrupted field rejected.
- Verify the root binding: a thread started under root A, resumed with the
  variable pointed at root B, exits non-zero and names neither path.
- Verify the boundary: a thread started without `oracle`, resumed with
  `--capability oracle`, exits non-zero and names the disagreement.

## 5. Keep the capability out of the terminal and the bundle

The Oracle root is a personal path, and the existing scan does not cover it.
`validatePortableFiles(files, manifest)` in `src/bundle/validate.ts:31` takes
its literals from `manifest.forbiddenLiterals`, a static declaration in
`agent-bundle.toml` that today reads
`literals = ["/Users/dongminyu", "/Volumes/dongminyu"]`.
A root under either prefix is caught by accident of this machine's layout; a
root anywhere else is not scanned at all, because the runtime value never
reaches the validator.

So do not extend the fixtures — that would add the chosen path to the fixture
manifest and prove only that a literal already in the list is caught, which is
a vacuous pass on the exact property this step exists to protect.
Thread the canonical runtime root into validation instead, as a literal
supplied alongside the manifest's rather than merged into it, so the scan
covers whatever root the operator actually set.
Nothing in the renderer prints the root, and no diagnostic quotes it.

- Verify with a root the manifest does not know: `pnpm test:unit` renders a
  file containing an Oracle root chosen to be absent from
  `forbiddenLiterals`, and asserts the scan rejects it.
- Verify it is not vacuous: the same case must pass the scan when the runtime
  root is not threaded through, and fail once it is.
- Verify by reading: grep the run and resume diagnostics for the variable and
  confirm no site interpolates its value.

## 6. Doctor reports the capability

`doctorCommand` passes an empty requested set of its own.
Have it report which capabilities the current environment would enable, as a
finding rather than a blocker, so an operator can tell an Oracle-off run from
an Oracle-on one before spending a turn.

- Verify: `pnpm test:integration` covers `doctor` with and without the
  variable set.

## Definition of Done

The acceptance bar is the operator's, restated here so a later session does
not re-derive it:

- A run without the flag behaves as v0.1 does, at the same bundle digest.
- The adapter and the external requirement are reached only on explicit
  opt-in.
- `resume` holds the same capability boundary as the run it continues.
- An absent, failing, or malformed Oracle never widens ordinary coding
  permission.
- Across five real tasks where past decisions matter, relevant precedent is
  retrieved.
- In at least three of those five, the retrieval demonstrably changed a design
  decision or an implementation direction.
- Irrelevant or stale retrieval is not treated as authoritative fact.
- No personal path, secret, or session datum reaches the bundle or the
  terminal.

The last four are measured by running the agent, not by a test.
Record that measurement in `docs/notes/` the way both dogfooding runs were
recorded, with the five tasks named and the three claimed helps each backed by
what the retrieval actually returned.
